- PROJECT.md

目标不是做规避型系统，而是做合法、透明、可审计的多租户支付、风控、财资调度中台。

重要边界：
1. 不实现无履约、不对版收单、隐藏真实交易、误导消费者、规避银行/卡组织/收单机构/LP/交易所/监管审查的能力。
2. 不实现前端混淆来规避风控。SDK 只能做透明接入、展示金额/商户/订单/退款政策。
3. 不实现争议资金、未履约资金、reserve 资金、manual_review 资金的自动上链或自动转移。
4. 所有外部资金动作必须走 Outbox / Worker / Saga。
5. DB 本地事务内禁止 LP / Bank / Exchange / MAE / HTTP 外部网络 I/O。
6. 敏感密钥必须加密，不得存 JSONB 明文。
7. Timeout != Failed，必须进入 UnknownExternalState，只能查询最终态，不盲目重复提交资金动作。
8. 不允许 stub、假成功、空实现冒充完成。

请按以下顺序执行。每次只做一个任务包，做完测试通过后再进入下一个。

============================================================
任务包 D：Dispute Ledger / Refund / Chargeback
============================================================

目标：
补齐退款、拒付、拒付反转的逆向账务与平台风险准备金。

涉及文件建议：
- migrations/
- internal/dispute/domain/
- internal/dispute/repository/
- internal/dispute/service/
- internal/dispute/handler/
- internal/ledger/
- internal/payout/ 或 internal/webhook/consumer/ 中涉及逆向事件入口的部分

要求：
1. 新增 payment_dispute 表。
2. 新增 platform_dispute_reserve_ledger 表。
3. 新增必要的 merchant_negative_balance 或等价追缴记录能力。
4. 新增 ledger transaction types：
   - ORDER_REFUND
   - CHARGEBACK_RECEIVED
   - CHARGEBACK_REVERSED
   - CHARGEBACK_FEE
5. 实现 RefundConfirmed 入账：
   - Dr Merchant Settled
   - Cr Acquirer Receivable / Bank Clearing
   - merchant settled 正确减少
6. 实现 ChargebackReceived 入账：
   - dispute amount 从 merchant settled 扣减
   - dispute amount 进入 platform dispute reserve
   - chargeback fee 单独进入 fee account
7. 实现 ChargebackReversed 入账：
   - 从 platform dispute reserve 转回 merchant settled
8. 如果 settled 不足：
   - settled 扣到 0
   - 差额进入 negative balance / receivable
   - merchant 进入 RiskHold 或等价状态
9. 所有写操作必须幂等。
10. 所有账务更新必须在一个 DB 本地事务内完成。
11. 不允许 webhook handler 直接改余额；必须进入 service/consumer 事务路径。

验收测试：
- refund 后 merchant settled 正确减少
- chargeback 后 reserve 正确增加
- chargeback fee 正确入 fee account
- reversed 后 merchant settled 恢复
- 重复 webhook / 重复 idempotency key 不重复入账
- settled 不足进入 negative balance / RiskHold
- 借贷分录恒平衡

============================================================
任务包 B：Anti-Carding Redis Sliding Window Gateway
============================================================

目标：
在 /public/v1/order-intents 前增加统一测卡/异常流量拦截。

涉及文件建议：
- internal/risk/carding/
- internal/platform/redis/
- internal/platform/httpx/
- cmd/api/main.go
- migrations/ 可新增 risk_event 表

要求：
1. 新增 RiskDecision：
   - Allow
   - Block
   - Challenge
   - Cooldown
2. 支持维度：
   - buyer_ip
   - app_id
   - tenant_id
   - merchant_id
   - card_bin_hash
   - device_hash
3. 使用 Redis Lua 原子 INCR + EXPIRE。
4. 支持 60s / 5m / 1h 窗口。
5. 命中阈值返回 429 或 403。
6. 命中阈值后不得调用后方 acquirer。
7. 写 risk_event 审计表。
8. 不存完整卡号，不存 CVV。BIN 必须 hash 或只保留统计所需最小信息。
9. Redis 不可用时：
   - local/mock 可配置 fail-open
   - production 默认 fail-closed

验收测试：
- 同 IP 60s 超阈值 -> Block
- 同 BIN 多卡失败 -> Block
- 同 App_ID 短时间高失败率 -> Block
- 正常低频请求 -> Allow
- 命中 Block 时确认没有调用 mock acquirer
- Redis Lua 脚本并发下计数正确

任务包 A：Channel Registry Object Pool
============================================================

目标：
实现动态通道客户端单例对象池，消除交易热路径查库、解密、创建 client。

涉及文件建议：
- migrations/
- internal/acquirer/registry/
- internal/acquirer/factory/
- internal/acquirer/adapter/
- internal/platform/config/
- cmd/api/main.go
- cmd/worker/main.go

要求：
1. 新增 payment_provider 表。
2. 新增 tenant_acquirer_channel 表。
3. 新增 provider_credential_vault 表。
4. provider_config 只存非敏感 JSONB 参数。
5. API key、secret、private key、webhook secret 必须进入 provider_credential_vault 加密存储。
6. 定义 AcquirerClient interface，至少包含：
   - Authorize
   - Capture
   - Refund
   - QueryPayment
   - VerifyWebhook
7. 实现 MockAcquirer adapter。
8. 实现 ChannelRegistry：
   - Get(channelID)
   - LoadAll(ctx)
   - Reload(channelID)
   - Disable(channelID)
9. 使用 RWMutex、sync.Map 或 atomic snapshot。交易热路径不得访问 PG/KMS。
10. Redis Pub/Sub 订阅 channel.config.updated 事件并触发 Reload。
11. Reload 成功后原子替换 ClientBundle。
12. Reload 失败必须 fail-closed 或 stale-but-serving，并输出日志和指标。
13. 禁用 channel 后 registry 不能继续返回可用 client。

验收测试：
- go test ./internal/acquirer/... -count=1
- 并发 1000 goroutine Get 不 race
- 修改 channel version 后 Reload 替换 bundle
- 禁用 channel 后 Get 返回 unavailable
- 交易热路径测试中不得查 PG/KMS，可用 mock store 断言调用次数为 0

============================================================

目标：
实现合规透明的站点接入 API，不实现规避型混淆。

涉及文件建议：
- migrations/
- internal/siteapp/
- internal/publicapi/
- web/sdk/

要求：

============================================================
任务包 C：Cashout Conversion Slippage Guard
============================================================

目标：
为自动化换汇增加 order book 检查、滑点保护、断点续传。

注意：
此任务必须最后做，因为它依赖账务、风控、对账基础。

涉及文件建议：
- migrations/
- internal/treasury/cashout/
- internal/worker/cashout/
- pkg/external/exchange/

要求：
1. 新增 treasury_cashout_policy 表。
2. 新增 treasury_cashout_request 表。
3. 新增 treasury_cashout_step 表。
4. 定义 ExchangeClient：
   - GetOrderBook
   - PlaceLimitOrder
   - QueryOrder
   - Withdraw
5. Conversion Worker 执行前必须读取 order book。
6. 默认 max_allowed_slippage_bps = 20，也就是最大 0.2%。
7. 超滑点 -> ApprovalRequired，不下单。
8. timeout -> UnknownExternalState。
9. partial fill -> PartiallyFilled，并记录 actual_target_amount。
10. 所有外部调用必须在 DB 事务外。
11. 有 provider_ref 时恢复只能 Query，不得重复 PlaceOrder。
12. 不可动用以下资金：
    - pending balance
    - reserve balance
    - dispute hold
    - frozen payout balance
    - manual_review 资金

验收测试：
- order book 深度不足 -> ApprovalRequired
- 滑点 <= 20bps -> 可提交 limit order
- timeout 不重复下单，只 query
- partial fill 不丢失实际成交金额
- manual_review / reserve / dispute hold 资金不可进入 cashout
